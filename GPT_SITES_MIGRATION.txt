TOY LEAGUE -> GPT SITES MIGRATION GUIDE
========================================

Last reviewed: 2026-09-19

Purpose
-------

Move the existing Toy League React/Vite project to GPT Sites while keeping the
current GitHub Pages quick game available at:

https://mingyuan7200.github.io/toy-league/

The two deployments do not need identical backend behavior:

1. GitHub Pages may continue to provide only the frontend quick game.
2. GPT Sites will host the personal version with persistent league data.
3. GPT Sites will use its built-in D1 relational database.
4. The GPT Site should remain private and accessible only by its owner.


EXPECTED ARCHITECTURE
---------------------

GitHub Pages deployment:

    Phone/browser
        -> GitHub Pages
        -> React quick game
        -> No required backend

GPT Sites deployment:

    Phone/browser
        -> Private GPT Site
        -> React quick game and league interface
        -> Server-side application routes
        -> D1 relational database


WHO DOES WHAT
-------------

Codex can do in this repository:

- Inspect and prepare the React/Vite source.
- Preserve the existing quick game.
- Make the build compatible with GPT Sites.
- Add league, player, stage, match, and result models.
- Add server-side D1 database access.
- Add database migrations.
- Add result history and data export/import.
- Test the frontend and production build.
- Review changes generated by Sites.
- Commit and push source changes when requested.

The user must do in ChatGPT/GPT Sites:

- Open the Sites workflow under the correct ChatGPT account.
- Select or attach the local Toy League project.
- Approve creation of the Site and its D1 storage.
- Review the saved preview version.
- Choose the owner-only access setting.
- Trigger the final deployment.
- Open the production URL on the phone.

Sites creation, storage provisioning, sharing, and production publishing are
account-level operations and are not performed from the Codex terminal UI.


PHASE 1: PREPARE AND PROTECT THE CURRENT PROJECT
------------------------------------------------

1. Confirm that the working tree is clean or understand every uncommitted
   change before editing.

2. Confirm that the current application builds successfully:

       npm install
       npm run build

3. Record the current working GitHub Pages URL and test the quick game before
   migration work begins.

4. Keep the existing game logic independent of hosting and persistence where
   practical. The number-game engine should not directly know whether data is
   stored in D1, local storage, or nowhere.

5. Do not manually invent a GPT Sites project ID. Sites assigns it when it
   provisions the hosted project.


PHASE 2: MAKE THE FRONTEND DEPLOYMENT-AWARE
-------------------------------------------

The current Vite configuration uses the GitHub Pages base path:

    /toy-league/

GPT Sites may serve the application from the root path instead. Prepare the
build so the base URL can differ by deployment, or let Sites make the required
compatibility change during import.

The desired behavior is:

- GitHub Pages assets continue loading under /toy-league/.
- GPT Sites assets and routes load under its own hosted URL.
- The quick game remains usable even when the database is unavailable.
- League/database controls on GitHub Pages may be hidden or disabled.

Because the user does not require backend features on GitHub Pages, it is fine
for D1-specific routes to exist only in the Sites runtime.


PHASE 3: DEFINE THE FIRST DATABASE SCHEMA
-----------------------------------------

A practical initial schema is:

leagues
    id
    name
    format
    status
    created_at
    updated_at

players
    id
    name
    created_at
    updated_at

league_players
    league_id
    player_id
    seed
    joined_at

stages
    id
    league_id
    name
    format
    stage_order
    status

matches
    id
    league_id
    stage_id
    round_number
    player_one_id
    player_two_id
    winner_id
    status
    scheduled_at
    completed_at

game_results
    id
    match_id
    player_one_value
    player_two_value
    winner_id
    result_data
    created_at

Notes:

- Use stable IDs rather than player names as references.
- Store canonical match results; calculate standings from those results where
  practical.
- Include schema migrations from the beginning.
- Start with one simple league format if necessary. Round-robin, single
  elimination, double elimination, and combined stages can be added through
  the stages model rather than hard-coding every combination immediately.
- Since this is initially a single-user private Site, a separate application
  login system is not required if Site access is owner-only.


PHASE 4: PREPARE APPLICATION FEATURES
-------------------------------------

Before or during the Sites conversion, implement these boundaries:

1. Quick game
   - Preserve current gameplay.
   - Allow a completed game to produce a structured result.

2. Persistence layer
   - Define functions for creating and reading leagues, players, matches, and
     results.
   - Implement these functions against D1 for GPT Sites.
   - Do not expose raw database credentials to browser code.

3. Basic management UI
   - Create a league.
   - Add or select players.
   - Start a match.
   - Save the completed match result.
   - View previous matches.

4. Backup
   - Export league data as JSON.
   - Ideally support importing a previously exported JSON file.
   - Treat D1 as the active database, but keep exports in case the beta service
     changes or the application later moves elsewhere.


PHASE 5: OPEN GPT SITES
-----------------------

1. Use a ChatGPT account with Sites access. According to the current official
   documentation, Sites is in public beta and is available with Plus, Pro,
   Business, Enterprise, and Edu plans. Plan-specific limits apply.

2. Open:

       https://chatgpt.com/sites

3. In the ChatGPT desktop app, open the local Toy League project if the Sites
   workflow offers the local-project path. Sites can also be managed on the
   web, but the desktop application is useful when starting from local source.

4. Start the Sites workflow by mentioning @Sites.


PHASE 6: USE THIS INITIAL SITES PROMPT
--------------------------------------

Copy and paste this prompt:

    @Sites Deploy this existing Toy League React/Vite project as a hosted
    website. First check whether the existing project is compatible with
    Sites and make only the required deployment changes.

    Preserve the current quick number game, its behavior, and its
    mobile-friendly interface.

    Add a D1 relational database for persistent leagues, players, league
    membership, tournament stages, matches, and game results. Saved data must
    remain available after refreshing, closing, and reopening the website.

    This is a personal application used only by me. Keep access restricted to
    the owner. Keep authorization and database access in server-side code.

    Save a reviewable version first, but do not deploy it to production yet.

If the repository has not yet received its database implementation, Sites may
generate or adapt the necessary server code and migrations. Review all such
changes before deployment.


PHASE 7: ALLOW SITES TO PROVISION D1
------------------------------------

For saved records, progress, and game scores, ask Sites to use D1. R2 object
storage is unnecessary unless the application later accepts avatars, images,
documents, audio, or other file uploads.

After provisioning, Sites may add a file resembling:

    .openai/hosting.json

Example shape:

    {
      "project_id": "<generated-project-id>",
      "d1": "DB",
      "r2": null
    }

Important:

- Let Sites generate the real project_id.
- Keep the binding name consistent with the server code.
- Do not put passwords, access tokens, or secret values in hosting.json.
- Do not commit local .env files containing secrets.


PHASE 8: REVIEW THE SAVED VERSION
---------------------------------

Do not deploy immediately. Test the saved preview/version first.

Frontend checks:

- The application loads without a blank page.
- CSS and JavaScript assets load from the correct paths.
- The quick number game behaves as it did on GitHub Pages.
- Buttons and inputs work at phone width.
- Text and controls are not clipped on a small screen.
- Touch targets are comfortable to use.

Database checks:

- Create a test league.
- Add at least two players.
- Create or start a match.
- Finish the number game.
- Save the result exactly once.
- Refresh the page and confirm the result remains.
- Close the browser, reopen the preview, and confirm the data remains.
- Confirm that starting or resetting a quick game does not delete history.
- Confirm that repeated taps do not create duplicate results.
- Confirm that invalid matches cannot be saved.

Privacy checks:

- Site access is restricted to the owner.
- Database writes happen through server-side code.
- No secrets appear in browser source or bundled JavaScript.
- No unnecessary personal information is stored.

Migration checks:

- Read every generated database migration.
- Ensure a migration does not drop existing tables or data unexpectedly.
- Confirm that schema changes can be applied only once safely.


PHASE 9: DEPLOY THE REVIEWED VERSION
------------------------------------

After the saved version passes review, give Sites this prompt:

    Deploy the reviewed saved version. Keep access restricted to the Site
    owner only. After deployment, provide the production URL.

Every Sites deployment URL is a production deployment. Saving a version and
deploying a version are separate steps, which is why review should happen
before this command.


PHASE 10: TEST ON THE PHONE
---------------------------

1. Open the production Sites URL on the phone.
2. Sign into the same ChatGPT account if requested.
3. Create a temporary league and two players.
4. Play and save a match.
5. Refresh the page and verify the result.
6. Close the browser completely.
7. Reopen the production URL and verify the result again.
8. Test both portrait and landscape orientation if relevant.
9. Optionally use the browser's Add to Home Screen function.
10. Delete the temporary test league only after persistence is confirmed.


PHASE 11: PRESERVE THE SITES SOURCE CHANGES
-------------------------------------------

After Sites modifies or provisions the project:

1. Review all changed files.
2. Retain useful server routes, schema, and migrations.
3. Retain .openai/hosting.json unless the Sites workflow says otherwise.
4. Verify that no secrets are staged in Git.
5. Run the local frontend build again.
6. Test the GitHub Pages quick game if shared frontend code changed.
7. Commit the reviewed source.
8. Push it to GitHub when ready.

The source repository should remain the long-term record of the application,
even though deployment and D1 provisioning are managed by GPT Sites.


PHASE 12: FUTURE LEAGUE DEVELOPMENT
-----------------------------------

A sensible implementation order is:

1. Persistent quick-game results.
2. Player management.
3. Simple leagues and match history.
4. Round-robin scheduling and standings.
5. Single-elimination brackets.
6. Double-elimination brackets.
7. Multi-stage combinations such as round-robin groups followed by playoffs.
8. Import/export, archive, and restore tools.

Keep tournament generation separate from React UI and database code. The
tournament engine should accept players and rules, then produce stages and
matches. This makes it easier to test and add formats later.


ROLLBACK AND SAFETY
-------------------

- Do not delete the GitHub Pages deployment during the migration.
- Do not deploy the first generated Sites version without preview testing.
- Export important league data periodically.
- Keep database migrations in source control.
- Keep the Site owner-only until sharing is intentionally needed.
- If a Sites deployment is bad, use the Sites version history to identify and
  redeploy a previously reviewed version when that option is available.
- Restricting access is different from deleting a Site. Permanent deletion
  cannot be restored according to the current documentation.
